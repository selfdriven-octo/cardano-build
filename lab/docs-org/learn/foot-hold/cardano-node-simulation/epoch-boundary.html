Cardano Consensus

Epoch Boundary

Every 5 days, the Cardano ledger performs its most computationally expensive operation: stake snapshot, reward calculation, pool retirement, protocol parameter updates, and nonce evolution. This is the #1 source of memory leaks — and the 10-day challenge test includes exactly two of these.

The 10-Day Memory Test: The challenge requires average memory usage matching or beating the Haskell node across 10 days. With epochs lasting ~5 days, that's two epoch boundaries. Each boundary causes a temporary memory spike of 2-4GB in the Haskell node (on top of baseline ~12GB for the UTxO set). If your node doesn't free this memory after the boundary processing completes, you fail. The Haskell team has spent years finding and fixing these space leaks.

The Three-Epoch Snapshot Delay
Cardano uses a snapshot from two epochs ago for block production and rewards. This delay is essential for security — it prevents stake grinding attacks where a pool changes stake to influence leader election.
Why the Delay Matters
Epoch N: Stake snapshot TAKEN (mark snapshot) ├─ Records: every wallet's delegation + every pool's total stake ├─ This is the "mark" snapshot — marks the boundary └─ ~1.3 million delegators × ~3,000 pools Epoch N+1: Snapshot becomes the "set" snapshot ├─ Used for NOTHING yet — just waiting └─ But must be kept in memory/disk Epoch N+2: Snapshot becomes ACTIVE ("go" snapshot) ├─ Used for VRF leader election this epoch ├─ Used for reward calculation at end of this epoch └─ Finally used, 2 full epochs after being taken Memory implication: Your node must maintain THREE snapshots simultaneously: 1. The "go" snapshot (currently active for leader election) 2. The "set" snapshot (waiting, will be active next epoch) 3. The "mark" snapshot (just taken, will be "set" next epoch) Each snapshot is ~400MB on mainnet. That's 1.2GB just for snapshots. The Haskell node uses sharing (common data referenced, not copied) to reduce this. A naive implementation stores 3 full copies = 1.2GB wasted.
Reward Distribution Algorithm
Step 1: Total Available Rewards reserves = totalADA - circulatingADA totalReward = ρ × reserves + η × fees where ρ = monetaryExpansion (0.003) and η = treasuryExpansion (0.2) Step 2: Per-Pool Rewards For each pool p with relative stake σ_p and blocks produced n_p: performance = n_p / expected_blocks(σ_p) poolReward = totalReward × σ_p × min(performance, 1) But capped by the pledge influence: pledge_factor = (1 + a0 × (pledge/saturation)) / (1 + a0) where a0 = poolPledgeInfluence (0.3) Step 3: Operator vs Delegator Split For each pool: operatorReward = min(poolReward, fixedCost) + margin × (poolReward - fixedCost) delegatorShare = poolReward - operatorReward For each delegator d with relative stake σ_d within the pool: delegatorReward_d = delegatorShare × (σ_d / pool_total_stake) Step 4: Treasury Cut treasury += τ × totalReward where τ = treasuryCut (0.2, i.e. 20%) Remaining 80% goes to pools + delegators Precision requirement: All calculations use rational arithmetic (not floating point!) A 1-lovelace difference = your node disagrees with Haskell node ~1.3M reward calculations per epoch boundary

Epoch Nonce Evolution Chain
The epoch nonce determines VRF leader election. It evolves each epoch by incorporating VRF outputs from blocks in the first 80% of the previous epoch. Getting the nonce wrong means your VRF evaluations produce different results — instant consensus failure.
Nonce Derivation Formula
η_e = hash( η_{e-1} ‖ η_v ‖ extra_entropy ) Where: η_{e-1} = previous epoch's nonce η_v = hash of all VRF outputs from blocks in slots 0 to ⌊0.8 × epochLength⌋ of epoch e-1 (only first 80% — the "stability window") extra_entropy = optional extra randomness from protocol params (currently null on mainnet, but was used at Shelley genesis) Why only the first 80%? If we used VRF outputs from the entire epoch, a pool that wins the last slot could choose whether to publish its block based on how the nonce would change — this is a "stake grinding" attack. Using only the first 80% means the nonce is determined before the last 20% of blocks, preventing this manipulation. The 4k/f parameter: The stability window is actually 3k/f = 3×2160/0.05 = 129,600 slots which is exactly 30% of an epoch (129600/432000 = 0.3). The nonce cutoff at 80% leaves a 20% buffer beyond the stability window.
The Memory Spike: At each epoch boundary, the Haskell node's memory usage temporarily spikes by 2-4GB as it computes rewards, takes snapshots, and processes retirements. This spike must be TEMPORARY — the memory must be freed after processing. If your implementation leaks even 100MB per epoch, after 2 epoch boundaries you've leaked 200MB and the 10-day average will exceed the Haskell node's.
