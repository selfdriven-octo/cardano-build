The Three Key Types
Cold Key (Ed25519) — The pool's master key
├─ Stored OFFLINE (cold storage, never on the block producer)
├─ Used to: sign operational certificates, register pool, retire pool
├─ If compromised: pool is permanently compromised
├─ Rotation: can delegate to new hot key via new OpCert
└─ The Haskell node NEVER loads the cold key

KES Key (Sum₆₂ MMM Composition) — Key-Evolving Signature
├─ Hot key that changes every KES period (129,600 slots ≈ 36 hours)
├─ Uses Merkle tree-based key evolution: 62 periods max
├─ After 62 evolutions: MUST generate new KES key + new OpCert
├─ The KES counter in the block header must match the current period
├─ Forward-secure: old KES keys are erased, preventing retroactive forgery
└─ Generated from KES secret key → evolves via node_kes_evolve()

VRF Key (ECVRF-ED25519-SHA512-Elligator2) — Slot Leadership Proof
├─ Evaluates: VRF_prove(vrf_skey, slot ‖ epoch_nonce)
├─ Output determines slot leadership: output < threshold ⟹ leader
├─ Threshold = 2^512 × φ_f(σ) where φ_f(σ) = 1 - (1-f)^σ
├─ The VRF proof is included in the block header for verification
├─ Also used to contribute to the next epoch's randomness (η_v)
└─ Must be registered on-chain via pool registration certificate

Operational Certificate — Links Cold ↔ KES
├─ Signed by cold key, contains: KES verification key + counter + start period
├─ Counter must be strictly greater than the last-seen counter for this pool
├─ If counter goes backward: indicates cold key compromise → pool banned
├─ Generated offline: cardano-cli node issue-op-cert
└─ Loaded by node at startup, refreshed when KES key rotates

Complete Block Structure (Babbage/Conway)
block = [header, transaction_bodies, transaction_witnesses, auxiliary_data, invalid_transactions] header = [header_body, kes_signature] header_body = { 0: block_number, -- monotonically increasing 1: slot, -- slot this block was forged in 2: prev_hash, -- hash of previous block header 3: issuer_vkey, -- pool's KES verification key 4: vrf_vkey, -- pool's VRF verification key 5: vrf_result, -- [vrf_output, vrf_proof] for this slot 6: block_body_size, -- byte size of the block body 7: block_body_hash, -- Blake2b-256 of encoded block body 8: operational_cert, -- [hot_vkey, sequence_number, kes_period, cold_sig] 9: protocol_version -- [major, minor] (9.0 for Conway) } kes_signature = -- KES signature over the serialized header_body -- Uses Sum₆₂ MMM signature scheme -- Key is evolved to the current KES period -- Verification uses the hot_vkey from the OpCert transaction_bodies = [tx_body_0, tx_body_1, ...] -- CBOR-encoded transaction bodies (map format post-Alonzo) -- Ordered by: phase-1-valid first, then by mempool arrival order -- Total size ≤ maxBlockBodySize (90,112 bytes on mainnet) transaction_witnesses = [witness_set_0, witness_set_1, ...] -- Parallel array: witnesses[i] corresponds to bodies[i] -- Each set: {vkey_witnesses, native_scripts, plutus_scripts, datums, redeemers} auxiliary_data = {index: metadata, ...} -- Transaction metadata (labels → values) -- Sparse map: only transactions with metadata are included invalid_transactions = [index_0, index_1, ...] -- Indices of transactions that FAILED Phase 2 (script execution) -- These transactions are included but their effects are NOT applied -- Only their collateral is consumed -- If your node omits these, the block body hash won't match
Critical: The Block Body Hash
The block_body_hash in the header is computed as:
Blake2b-256( CBOR_encode( [tx_bodies, tx_witnesses, auxiliary_data, invalid_txs] ) )
If ANY of these are wrong — wrong transaction order, non-canonical CBOR, missing invalid_transactions indices, wrong witness alignment — the hash changes and every other node rejects your block.
This is the single most common failure mode for alternative node implementations attempting block production.
