The Invisible Layer: All four mini-protocols (ChainSync, BlockFetch, TxSubmission, KeepAlive) share a single TCP connection. The multiplexer is the framing layer that interleaves their messages, prevents one protocol from starving others, and handles segmentation of large payloads.
Multiplexer Frame Format
┌─────────────────────────────────────────────────────────────┐
│                    MUX SEGMENT HEADER (8 bytes)             │
├──────────┬──────────┬──────────────────────────────────────┤
│ Timestamp │ Mini-Proto│ Payload Length                      │
│ 4 bytes  │  2 bytes │ 2 bytes                              │
│ (μs,     │  (ID +   │ (max 65535                           │
│  32-bit) │  mode)   │  bytes)                              │
├──────────┴──────────┴──────────────────────────────────────┤
│                                                             │
│                    PAYLOAD (0..65535 bytes)                  │
│                    (CBOR-encoded mini-protocol message)      │
│                                                             │
└─────────────────────────────────────────────────────────────┘

Protocol IDs (Node-to-Node):
  0 = Handshake        3 = BlockFetch
  2 = ChainSync         7 = TxSubmission2
  8 = KeepAlive

Mode bit (bit 15 of protocol ID field):
  0 = Initiator (client)
  1 = Responder (server)

Node-to-Client protocol IDs differ:
  0 = Handshake        5 = ChainSync (full blocks)
  3 = LocalTxSubmission 6 = LocalStateQuery

The Serialization Minefield: Every byte on the Cardano wire is CBOR. The CDDL spec defines the exact encoding for each era. A single extra byte, a wrong CBOR major type, or a missing tag will cause the receiving node to reject your message and disconnect. And the encoding differs across all 7 eras.
CBOR Encoding Examples
-- MsgRollForward (ChainSync) carries a block header
-- The CBOR structure differs by era:

-- Byron block header (simplified):
[0,            -- era tag: 0 = Byron
 [0,           -- boundary vs main block
  [header_hash, -- 32 bytes Blake2b-256
   [... consensus data ...
    [slot_id,    -- [epoch, slot_in_epoch]
     pub_key,    -- 64 bytes Ed25519
     difficulty, -- chain difficulty number
     signature  -- 64 bytes Ed25519
    ]]]]

-- Shelley+ block header (simplified):
[1,            -- era tag: 1+ = post-Byron
 [header_body, -- the actual header fields:
  [block_no,    -- unsigned integer
   slot,        -- unsigned integer
   prev_hash,   -- 32 bytes (or null for genesis)
   issuer_vkey, -- 32 bytes VRF verification key
   vrf_result,  -- [vrf_output, vrf_proof]
   body_size,   -- block body size in bytes
   body_hash,   -- 32 bytes Blake2b-256
   op_cert,     -- [hot_vkey, seq_no, kes_period, sig]
   protocol_ver -- [major, minor]
  ],
  kes_signature -- KES signature over header body
 ]]

-- Transaction (Babbage/Conway era):
[tx_body,       -- map of field_id → value
 witness_set,   -- map: vkey_witnesses, scripts, datums, redeemers
 is_valid,      -- boolean (Plutus phase-2 validity flag)
 auxiliary_data -- metadata (or null)
]

The Largest Codebase: The ledger rules are the single biggest component of a Cardano node — roughly 80,000+ lines of Haskell in cardano-ledger. They define every validity check for every transaction type across every era. Getting even one rule wrong means your node accepts invalid transactions or rejects valid ones.
Transaction Validation Pipeline (Babbage/Conway)
  Transaction arrives (from TxSubmission or block body)
  │
  ├─ Phase 1: Structural Validation
  │  ├─ CBOR well-formed for current era?
  │  ├─ Tx size ≤ maxTxSize protocol parameter?
  │  ├─ All inputs reference existing UTxOs?
  │  ├─ No double-spending (input appears only once)?
  │  ├─ Validity interval includes current slot?
  │  ├─ Fee ≥ calculated minimum fee?
  │  │    └─ minFee = txFeeFixed + txFeePerByte × txSize
  │  │       + Σ(executionUnitPrices × scriptExUnits)
  │  ├─ Preservation of value (inputs = outputs + fee)?
  │  ├─ All output values ≥ minUTxOValue?
  │  ├─ Required signers present?
  │  ├─ Collateral provided (if scripts present)?
  │  │    └─ collateral ≥ collateralPercentage × fee
  │  └─ Network ID matches (if specified)?
  │
  ├─ Phase 2: Script Execution (if tx has scripts)
  │  ├─ For each Plutus script in witnesses:
  │  │  ├─ Deserialize script (PlutusV1/V2/V3)
  │  │  ├─ Build script context (ScriptPurpose → ScriptContext)
  │  │  ├─ Apply cost model for this Plutus version
  │  │  ├─ Execute in CEK machine with budget limit
  │  │  │    └─ Budget = (cpu_steps, memory_units) from redeemer
  │  │  ├─ Script must return True
  │  │  └─ Actual cost must ≤ declared budget
  │  ├─ For native/timelock scripts:
  │  │  └─ Evaluate time/signature predicates
  │  └─ If ANY script fails → tx is INVALID
  │     └─ But if Phase 1 passed, collateral is still consumed!
  │        (This is the "two-phase validation" innovation)
  │
  ├─ Phase 3: UTxO Update
  │  ├─ Remove spent inputs from UTxO set
  │  ├─ Add new outputs to UTxO set
  │  ├─ Update delegation/stake state
  │  ├─ Process governance actions (Conway)
  │  └─ Accumulate fees for reward distribution
  │
  └─ Mempool / Block Integration
     ├─ If in mempool: add to pending set, propagate via TxSubmission
     └─ If in block: apply as part of block validation
        └─ Block-level checks: slot, issuer, VRF, KES, body hash
The Hard Fork Combinator — Era Transitions

The Haskell node doesn't implement 7 separate nodes — it uses the Hard Fork Combinator (HFC) to compose era-specific ledger rules into a single state machine. The HFC handles era transitions seamlessly: at the epoch boundary where a hard fork is scheduled, the ledger state is translated from the old era to the new one. Your alternative node must implement this translation for every era boundary.

  Byron ──epoch 208──→ Shelley ──epoch 236──→ Allegra ──epoch 251──→ Mary
                                                                      │
  Conway ←──epoch 520── Babbage ←──epoch 394── Alonzo ←──epoch 290──┘

  At each boundary:
  ┌──────────────────────────────────────────────────────────────┐
  │ 1. Protocol parameter update triggers era transition         │
  │ 2. translateLedgerState :: OldEra → NewEra                  │
  │ 3. New block/tx validation rules take effect                │
  │ 4. Old-era transactions in mempool are re-validated or purged│
  │ 5. Serialization format changes (new CDDL spec)             │
  └──────────────────────────────────────────────────────────────┘

  Your node must handle blocks from ANY era during sync.
  Block at slot 1 is Byron. Block at tip is Conway.
  The chain is one continuous sequence across all 7 eras.
Crash Recovery: The challenge explicitly requires surviving power loss at any point. ChainDB is the component that makes this possible — it uses a carefully designed on-disk layout with atomic operations so the database is always recoverable, even if the node is killed mid-write.
ChainDB Architecture
                         ┌───────────────────────────┐
                         │      Chain Selection       │
                         │  (Praos longest chain)    │
                         └─────────┬─────────────────┘
                                   │
                    ┌──────────────┼──────────────┐
                    │              │              │
              ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
              │ Volatile DB │ │  Ledger   │ │ Immutable │
              │           │ │  State    │ │    DB     │
              └─────┬─────┘ └─────┬─────┘ └─────┬─────┘
                    │             │              │
              Recent blocks  UTxO set +     Finalized blocks
              (last k)       delegation     (older than k)
              In-memory +    state          Append-only
              on-disk        Snapshots      chunk files
                             to disk

  Volatile DB: Stores the last k blocks (k=2160 on mainnet)
  ├─ Blocks that might still be rolled back
  ├─ Stored in individual files by block hash
  ├─ On startup: scan directory, reconstruct chain
  └─ Garbage collection: delete blocks not on current chain

  Immutable DB: Stores all finalized blocks
  ├─ Blocks with k+ confirmations (can never roll back)
  ├─ Append-only chunk files (~2000 blocks per chunk)
  ├─ Primary index: block_no → chunk + offset
  ├─ Secondary index: slot → block_no (for point lookups)
  └─ NEVER modified after write (crash-safe by design)

  Ledger State: The accumulated result of applying all blocks
  ├─ UTxO set (~15M entries on mainnet)
  ├─ Stake distribution, delegation map
  ├─ Protocol parameters, governance state
  ├─ Snapshots taken at epoch boundaries
  └─ In-memory for tip, on-disk for historical
  
  Key invariant: immutableTip + k ≤ volatileTip
  When a new block extends the chain past k confirmations,
  the oldest volatile block is MOVED to immutable storage.
Crash Recovery Protocol
  On startup after unclean shutdown:

  1. Recover Immutable DB
     ├─ Validate last chunk file (might be partially written)
     ├─ Truncate last chunk to last valid block
     ├─ Rebuild primary/secondary indices if needed
     └─ Immutable tip = last complete block in last chunk

  2. Recover Volatile DB
     ├─ Scan all block files in volatile directory
     ├─ Parse headers to reconstruct chain fragments
     ├─ Find the chain that connects to immutable tip
     ├─ Discard orphan blocks (not connected to any chain)
     └─ Volatile tip = tip of longest valid chain from immutable tip

  3. Recover Ledger State
     ├─ Load most recent ledger snapshot from disk
     ├─ If snapshot is at slot S, replay blocks from S+1 to tip
     ├─ This can take minutes for large gaps
     └─ Once caught up, resume normal operation

  4. Critical: Write Ordering
     ├─ Immutable DB: append block, THEN update index
     │   (if crash mid-write: truncate and re-index on recovery)
     ├─ Volatile DB: write block file, THEN update in-memory chain
     │   (if crash: orphan file is cleaned up on recovery scan)
     ├─ Ledger snapshots: write to temp file, THEN atomic rename
     │   (if crash: old snapshot is still valid)
     └─ NEVER: update index before writing data
         (this would create dangling pointers that corrupt the DB)
