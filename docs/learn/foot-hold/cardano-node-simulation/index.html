Building a Cardano Node
From Scratch

An interactive architecture guide to every subsystem a spec-compliant, block-producing Cardano node requires — from consensus to CBOR, multiplexer to mempool, ChainDB to crash recovery.

Context: This resource was created in response to an open challenge to vibe-code an alternative Cardano node from scratch. While AI can accelerate implementation, this guide demonstrates why a fully spec-compliant node is a multi-year engineering effort — and maps exactly which subsystems the challenge's acceptance tests verify.

Challenge Acceptance Criteria
What Each Test Verifies
Mapping the open challenge's acceptance tests to the subsystems they exercise.
① Sync from mithril snapshot or genesis to tip
Tests: ChainSync (header fetch), BlockFetch (body download), CBOR (all 7 eras), Ledger (full chain replay), ChainDB (storage), Multiplexer (framing)
② Produce a valid block on preview/preprod
Tests: Praos (VRF leader election, KES signing), Ledger (block construction), CBOR (canonical encoding), ChainSync (header propagation)
③ Node-to-client blockfetch & txsubmission
Tests: Multiplexer (N2C protocol IDs), LocalChainSync, LocalTxSubmission, CBOR (full block encoding)
④ Run in private testnet with 2 Haskell nodes
Tests: All protocols (interop), Praos (consensus agreement), KeepAlive (connection maintenance), Handshake (version negotiation)
⑤ Agree on tx validity with Haskell node
Tests: Ledger (all validation rules), Plutus VM (script execution + cost model), CBOR (canonical hashing)
⑥ Agree on block validity with Haskell node
Tests: Praos (VRF/KES validation), Ledger (block-level rules), Hard Fork Combinator (era transitions)
⑦ Agree on consensus tip within 2160 slots
Tests: Praos (chain selection, density rule), ChainSync (header evaluation), Epoch boundary (stake distribution)
⑧ Recover from power loss without human intervention
Tests: ChainDB (crash recovery protocol), Immutable/Volatile DB (atomic writes), Ledger Snapshots (replay from snapshot)
Additional: 10-day average memory usage must match or beat the Haskell node. This tests Ledger (UTxO set memory management), ChainDB (garbage collection), Mempool (tx eviction), and epoch boundary processing (memory spikes during reward calculation). The Haskell node has spent years finding and fixing space leaks — this is arguably the hardest requirement to meet.
