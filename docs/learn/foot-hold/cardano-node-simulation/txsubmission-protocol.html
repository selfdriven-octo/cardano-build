TxSubmission Mini-Protocol

Interactive simulator of the transaction submission protocol — uniquely designed with inverted control flow where the server (consumer) drives the conversation to prevent DoS attacks. Transactions are advertised by ID, then pulled on demand.

Key Design Insight: Unlike most protocols where the client pushes data, TxSubmission uses a pull-based model. The server asks "what do you have?" and then selectively requests specific transactions. This prevents a malicious peer from flooding the node's mempool — the server controls how many transactions it accepts and when.

-- TxSubmission2 protocol (the current version)
-- Key insight: SERVER has agency in the idle state
-- This is the opposite of most protocols!

data TxSubmission2 txid tx where

  StInit :: TxSubmission2 txid tx
    -- Server has agency (sends initial request)

  StIdle :: TxSubmission2 txid tx
    -- Server has agency (controls the flow!)

  StTxIds :: TxSubmission2 txid tx
    -- Client has agency (replies with tx IDs)

  StTxs :: TxSubmission2 txid tx
    -- Client has agency (replies with tx bodies)

  StDone :: TxSubmission2 txid tx

-- Server → Client (server drives the conversation):

MsgInit
  :: Message StInit StIdle

MsgRequestTxIds (blocking :: Bool) ack_count req_count
  :: Message StIdle StTxIds
  -- ack_count: how many previously advertised txids
  --            the server is done with (acknowledgement)
  -- req_count: how many NEW txids the server wants
  -- blocking: if True, client can block until it has txs
  --           if False, client must reply immediately

MsgRequestTxs [txid]
  :: Message StIdle StTxs
  -- Server requests specific transactions by ID
  -- (from previously advertised IDs)

-- Client → Server:

MsgReplyTxIds [(txid, SizeInBytes)]
  :: Message StTxIds StIdle
  -- Client sends transaction IDs + their sizes
  -- Server uses sizes for mempool accounting

MsgReplyTxs [tx]
  :: Message StTxs StIdle
  -- Client sends the actual transaction bodies

MsgDone
  :: Message StIdle StDone
